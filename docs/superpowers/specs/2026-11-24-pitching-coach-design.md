# 투수 코칭 시스템 설계 (v1)

작성일: 2026-11-24 · 상태: 초안(사용자 승인 대기)

## 1. 의도와 이유

투수 영상(측면/후면)을 넣으면 **투구 구간별 체크포인트**, **몸의 부위별 힘(에너지) 흐름**, **약한 고리를 키우는 운동 제안**을 보여주는 웹 기반 코칭 시스템.

- 대상: 프로 투수와 그 코치.
- 차별점: 기존 제품(TrackMan/Rapsodo = 공 데이터, KinaTrax/Uplift/Mustard류 = 스켈레톤·숫자·그래프)과 달리, **선수가 보자마자 "힘이 어디서 새는지" 몸으로 이해하는 시각화**.
- 현실 조건: 프로 선수·코치·데이터 접근 통로가 **없음**. 따라서 v1의 실질 목표는 "프로 코치가 링크로 보고 써보고 싶어지는 데모". 이를 통해 접근 기회를 얻는다.

## 2. 목표 / 비목표 / 반목표

**목표**
1. 측면 영상 1개(권장 ≥120fps)를 업로드하면 투구 구간을 자동 분할하고 구간별 체크포인트를 표시.
2. 다리 → 골반 → 몸통 → 팔 → 손(공) 순서의 에너지 흐름을 영상 위 오버레이로 시각화, 흐름이 끊기는(타이밍 어긋남/속도 손실) 지점을 강조.
3. 각 부위 점수(기준값 대비) 및 문제 → 가능한 원인 → 30초 자가 테스트 → 운동 제안.
4. 후면 영상(2단계): 릴리스 포인트 일관성, 팔 각도(arm slot), 몸통 측면 기울기, 스트라이드 방향 분석과 자세 교정 조언. Rapsodo/TrackMan CSV 가져오기(선택).
5. 브라우저 링크 하나로 데모 가능.

**비목표 (v1)**
- 힘(N)·토크(N·m)의 실측. 영상에서는 운동학(위치·각도·속도)만 얻는다. 화면의 "에너지/힘"은 운동학 기반 **추정 지표**다.
- 영상으로 회전수(rpm)·회전축 측정.
- 부상 진단.
- 계정/로그인, 결제, 모바일 네이티브 앱, 다중 카메라 3D.
- LLM 기반 자연어 코칭(후순위 확장).

**반목표 (기술적으로 돌아가도 실패로 보는 것)**
- 화면이 데이터보다 정확해 보이게 만드는 것. 모든 지표에 신뢰도(높음/중간/낮음)를 표시하고, 낮은 신뢰도 지표는 시각 효과를 약하게 한다.
- 운동을 "처방"처럼 보이게 하는 것. 항상 "제안"으로 표기하고, 원인이 자가 테스트로 좁혀지지 않으면 단정하지 않는다.
- 근거(출처) 없는 기준값 사용.

## 3. 제약

- 카메라 1대, 2D. 측면에서는 골반·어깨의 수평 회전(분리각)이 잘 보이지 않는다 → 회전 관련 지표는 "낮은 신뢰도".
- 프레임 속도: 30fps 영상은 릴리스 구간이 1~2프레임에 묻힌다. 120fps 미만이면 경고, 60fps 미만이면 타이밍 지표 비활성화.
- 크기 보정: 사용자가 키(cm)와 투구 손(좌/우)을 입력. 픽셀 → 미터 환산은 키 기준.
- 기준값은 공개 자료에서: Driveline **OpenBiomechanics Project**(라이선스, 특히 상업적 이용 가능 여부를 착수 전 확인 필수), Fleisig 등 투구 바이오메카닉스 논문. 모든 기준값은 출처와 함께 설정 파일에 저장.
- 검증 데이터가 없으므로, 초기 테스트는 공개 영상·본인/아마추어 영상·OpenBiomechanics 데이터로 한다.

## 4. 접근 방식 (검토한 것과 선택)

| | A. PC 분석 프로그램 | **B. 웹앱 (선택)** | C. 3D 아바타형 |
|---|---|---|---|
| 형태 | Python, 영상 → 분석 영상 출력 | 브라우저 업로드 → 인터랙티브 분석 화면 | 단안 2D → 3D 리프팅, 360° 회전 |
| 장점 | 가장 빠름 | 링크로 데모·영업 가능 | 시각적으로 가장 획기적 |
| 단점 | 공유 불편 | 서버 필요, A 대비 작업량 약 1.5배 | 단안 3D 깊이 오차 큼, 정확도 과장 위험 최고 |

**선택: B.** 가장 큰 리스크는 "접근 통로 없음"이고, 링크 공유 가능한 데모가 그것을 가장 직접적으로 푼다. 분석 엔진은 독립 Python 패키지로 만들어 CLI 단독 실행도 가능하게 하고(A의 장점 흡수), C는 추후 확장으로 둔다.

## 5. 결정된 설계

### 5.1 구조
```
[브라우저: React + TypeScript + Vite]
  업로드 / 분석 화면(영상 + Canvas 오버레이, 구간 타임라인, 부위 점수, 운동 제안)
        │ HTTP (REST)
[서버: Python FastAPI]
  업로드 저장 → 분석 작업(백그라운드) → 결과 JSON 제공
        │
[분석 엔진: Python 패키지 `pitchcoach`]  ← CLI로도 실행 가능
  포즈 추정 → 스무딩 → 구간 분할 → 지표 계산 → 기준값 비교 → 규칙 기반 진단/운동 제안
```
- 오버레이는 영상에 굽지 않고 브라우저에서 결과 JSON(프레임별 관절 좌표 + 지표)을 받아 실시간 렌더링한다. 재생/정지/프레임 이동/구간 점프가 가능해야 한다.
- 저장소: 로컬 디스크(업로드 영상, 결과 JSON). DB 없음(v1).

### 5.2 포즈 추정
- 기본: MediaPipe Pose(33 관절, 발뒤꿈치/발끝 포함 → 앞발 착지 판정에 유리). 포즈 추정기는 인터페이스 뒤에 두어 RTMPose 등으로 교체 가능하게.
- 관절 좌표 스무딩(예: Savitzky–Golay 또는 Butterworth 저역통과)은 필수. 필터 종류·차단 주파수는 빌더 재량이나 fps에 맞춰 조정.

### 5.3 구간 분할 (측면)
레그 리프트(최고점) → 스트라이드 → 앞발 착지 → 팔 코킹 → 가속/릴리스 → 팔로스루.
- 이벤트 정의(초안): 앞무릎 최고점, 앞발 발목 속도 ≈ 0 지속 시점(착지), 손목 전방 속도 최대 직후(릴리스).
- 어깨 최대 외회전(MER)은 측면 2D로 정확히 잡기 어려움 → "추정, 낮은 신뢰도"로 표시.

### 5.4 에너지 흐름 지표 (측면, 2D에서 실제로 측정 가능한 것 위주)
- 부위별 선속도: 무게중심(골반 중심) → 어깨 중심 → 팔꿈치 → 손목. **최고 속도의 순서와 시간 간격**(근위 → 원위 순서)이 핵심 지표.
- 측면에서 보이는 각도: 앞무릎 굴곡(착지~릴리스, 앞다리 블록), 몸통 전방 굴곡 각속도, 팔꿈치 신전 각속도, 보폭(키 대비 %).
- 회전 추정(골반·어깨): 화면상 좌우 관절 간 투영 폭 변화로 추정 → 낮은 신뢰도.
- 부위 점수(0~100): 기준값 분포 대비 위치. 점수 산식은 빌더 재량이되 설정 파일로 분리.

### 5.5 시각화 (차별점의 핵심)
- **에너지 흐름 오버레이**: 스켈레톤 위로 빛/흐름이 발 → 골반 → 몸통 → 팔 → 손으로 이동. 밝기/굵기 = 해당 부위 속도의 기준값 대비 비율. 순서가 어긋나거나 속도가 떨어지는 지점에서 "새는" 효과(입자가 흩어짐 등) + 빨간 표시.
- **구간 타임라인**: 영상 아래 구간 막대, 클릭하면 해당 이벤트 프레임으로 이동. 각 구간에 체크포인트 통과/주의 아이콘.
- **타이밍 고스트**: 기준값의 이상적 최고속도 타이밍을 타임라인 위 반투명 마커로 겹쳐, 내 타이밍과의 차이(ms)를 표시.
- **부위 점수 패널**: 다리/골반/몸통/팔 점수 막대 + 신뢰도 배지.
- 신뢰도 낮은 지표는 효과를 흐리게, 점선으로 표시.

### 5.6 진단과 운동 제안
- 규칙 기반. 설정 파일(JSON/YAML)로 관리: `문제 → 가능한 원인들 → 원인 구분용 자가 테스트 → 원인별 운동 제안(세트×횟수, 설명, 출처)`.
- 예: "골반 최고속도가 착지 대비 늦음" → 원인 후보(고관절 가동성 / 회전 파워 부족 / 타이밍 습관) → 자가 테스트(고관절 내회전 각도 체크 등) → 결과에 따라 메디신볼 회전 던지기, 고관절 가동성 루틴 등.
- 자가 테스트는 사용자가 화면에서 결과를 선택 입력. 미입력 시 원인 후보 전부와 각 운동을 "가능성"으로 나열.
- 모든 제안에 "트레이닝 코치와 상의 후 적용" 문구.
- 운동 라이브러리의 초기 내용 작성은 빌더가 공개 문헌 기반으로 하되, 출처 없는 항목은 넣지 않는다.

### 5.7 후면 영상 (2단계)
- 같은 영상에 여러 투구가 있으면 투구별로 분리.
- 지표: 릴리스 포인트(화면 좌표, 키로 정규화)의 투구 간 편차, 팔 각도, 몸통 측면 기울기, 스트라이드 방향(홈플레이트 쪽 정렬).
- 구질: 영상만으로는 "릴리스 일관성과 팔 각도 기반 해석"까지만. 회전수·무브먼트는 Rapsodo/TrackMan CSV를 가져왔을 때만 표시하고 동작 지표와 투구별로 연결.

### 5.8 입력 조건 안내
업로드 화면에 촬영 가이드: 측면은 투수 정면 90° 옆, 삼각대 고정, 전신이 프레임 안, 슬로모션(120~240fps). 조건 불충족(fps 낮음, 사람 미검출, 흔들림)은 결과 전에 경고.

### 5.9 설계 검토 후 확정한 사항 (작성자 판단, 사용자 확인 대상)
- **2D vs 3D 기준값 비교**: 3D 실험실 수치와 2D 측면 측정값을 직접 비교하지 않는다. OpenBiomechanics의 3D 마커 데이터를 **측면(시상면)으로 투영해 합성 2D 기준값**을 만들고, 그것과 비교한다. 투영 불가 지표(회전)는 점수에서 제외하고 참고값으로만 표시.
- **카메라 방향**: v1은 투구 팔 쪽 측면(우투수 기준 3루 쪽)만 지원. 글러브 쪽은 투구 팔이 몸에 가려 제외, 업로드 시 선택하게 하고 반대쪽이면 경고.
- **데모 형태**: 사전 분석된 샘플 클립 3~5개 + 임의 업로드(품질 검사 통과 시만 분석). 작업 비중은 시각화 우선.
- **UI 언어**: 한국어 기본, 문자열은 다국어 구조로 분리(영어 추가 대비).
- **업로드 보안**: 업로드마다 추측 불가능한 URL, 목록 노출 없음, 7일 후 자동 삭제.
- **v1 완료 기준**: 수작업으로 이벤트 프레임을 표시한 공개/아마추어 클립 20개에서 이벤트 검출 오차 120fps 기준 ±2프레임 이내 80% 이상.

## 6. 빌더 재량

- 스무딩 필터와 파라미터, 이벤트 검출 세부 임계값.
- 점수 산식, 시각 효과 구현 방식(Canvas 2D vs WebGL), UI 세부 디자인.
- 백그라운드 작업 방식(FastAPI BackgroundTasks / 간단한 큐).
- 테스트 전략(분석 엔진은 단위 테스트 필수, 합성 키포인트 데이터로 이벤트 검출 검증 권장).
- 배포 방식(v1은 로컬 실행 + 데모용 단일 서버면 충분).

## 7. 단계

1. 분석 엔진(측면): 포즈 추정, 구간 분할, 지표, 기준값 비교, CLI.
2. 웹앱: 업로드, 분석 화면, 에너지 흐름 오버레이, 타임라인, 점수, 운동 제안.
3. 후면 영상 분석 + CSV 가져오기.
4. (확장) 3D 아바타, 리듬 사운드, LLM 코칭.
